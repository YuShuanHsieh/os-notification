# Offline/air-gapped container image for the .NET build

## Purpose

The repo has no way to build or test the C# agent without network access to
`nuget.org` at restore time. To support running the existing validation
commands (`dotnet build` / `dotnet test` / `dotnet format`, per `AGENTS.md`) in
an air-gapped or network-restricted CI environment, we need a container image
that ships with everything pre-restored, and a documented, clearly separated
"refresh caches" step (needs network) versus "build/test offline" step
(network disabled).

Source: [issue #11](https://github.com/YuShuanHsieh/os-notification/issues/11).

## Scope

- **In scope:** a Docker image (`docker/dotnet-offline.Dockerfile`) built on
  the .NET 10 SDK, able to `dotnet build`/`dotnet test`/`dotnet format`
  `NotificationAgent.sln` (Core, Core.Tests, ConsoleHost, TestPublisher) and
  compile the Windows-only projects (`src/NotificationAgent.Windows`,
  `tests/NotificationAgent.Windows.Tests`, via `EnableWindowsTargeting`) with
  no network access at that point; `packages.lock.json` per project for
  reproducible, verifiable restores; a documented manual verification
  procedure.
- **Out of scope:** the Rust toolchain/image (issue #11 asks for it, but the
  Rust workspace only exists on the unmerged `rust-agent` branch / PR #4 —
  this design covers the .NET half now, and the Rust half is deferred to a
  follow-up issue/design once PR #4 merges into `main`); publishing the image
  to GHCR or any registry; a GitHub Actions CI workflow (this repo has none
  today; wiring one is a separate concern); running
  `NotificationAgent.Windows.Tests` inside the container — per `AGENTS.md`,
  that already requires a real Windows machine today, independent of this
  work; long-lived interactive containers with a live source bind-mount (this
  image is rebuilt fresh each time, like a CI image, not used as a persistent
  dev environment).

## Architecture

Two steps, deliberately separated so it's obvious which one needs network
access:

```
1. Refresh (needs network — the only step that talks to nuget.org):

   docker build -f docker/dotnet-offline.Dockerfile -t notification-agent-offline .

   FROM mcr.microsoft.com/dotnet/sdk:10.0
     ├─ COPY the full repo into the image (WORKDIR /repo)
     ├─ RUN dotnet restore NotificationAgent.sln --locked-mode
     └─ RUN dotnet restore src/NotificationAgent.Windows/NotificationAgent.Windows.csproj --locked-mode
        RUN dotnet restore tests/NotificationAgent.Windows.Tests/NotificationAgent.Windows.Tests.csproj --locked-mode
        (excluded from the .sln today per AGENTS.md; restored separately, same as `dotnet build`/`test` already treat them in AGENTS.md's validation commands)

   A `RUN` step immediately after the `COPY`, before any restore, checks that
   all six committed `packages.lock.json` files actually exist and fails the
   build with a clear message if one is missing (see Error handling below —
   `--locked-mode` alone does not catch a fully missing lock file).

   This bakes into image layers: the resolved NuGet global-packages cache
   (~/.nuget/packages) AND each project's obj/project.assets.json — both
   produced by a restore that ran with network access at `docker build` time.

2. Offline build/test (network disabled — this is the point being verified):

   docker run --rm --network none notification-agent-offline \
     dotnet build NotificationAgent.sln --no-restore
   docker run --rm --network none notification-agent-offline \
     dotnet test NotificationAgent.sln --no-restore
   docker run --rm --network none notification-agent-offline \
     dotnet format NotificationAgent.sln --verify-no-changes --no-restore
   docker run --rm --network none notification-agent-offline \
     dotnet build src/NotificationAgent.Windows/NotificationAgent.Windows.csproj --no-restore
   docker run --rm --network none notification-agent-offline \
     dotnet build tests/NotificationAgent.Windows.Tests/NotificationAgent.Windows.Tests.csproj --no-restore
```

`--no-restore` (already used for `dotnet format` in `AGENTS.md`) guarantees
MSBuild never attempts to reach a NuGet source, since every package is already
resolved to disk from step 1. `--network none` is what actually proves it:
if anything in the build/test/format path were to require network, it fails
loudly inside the sandboxed container rather than silently succeeding.

## Components

### `Directory.Build.props`

One new property, applied repo-wide (matching how analyzer settings are
already centralized here):

```xml
<RestorePackagesWithLockFile>true</RestorePackagesWithLockFile>
```

### `packages.lock.json` (one per project, 6 total, generated not hand-written)

`src/NotificationAgent.Core/`, `src/NotificationAgent.ConsoleHost/`,
`src/NotificationAgent.Windows/`, `tests/NotificationAgent.Core.Tests/`,
`tests/NotificationAgent.Windows.Tests/`, `tools/TestPublisher/`. Generated by
running `dotnet restore` once per project (network required, done during
implementation and again on future refreshes) and committed to git.
`--locked-mode` restore fails fast if a csproj's `PackageReference`s drift
without a matching lock-file update — that failure is the deliberate signal
telling a developer to refresh (rerun restore with network) and commit the
updated lock file, rather than silently reaching the network or silently
building against different packages than what's committed.

### `docker/dotnet-offline.Dockerfile`

Single-stage image as described in Architecture above. Uses
`mcr.microsoft.com/dotnet/sdk:10.0` (matching the `net10.0` /
`net10.0-windows10.0.19041.0` target frameworks already in use). Named to
leave room for a sibling `docker/rust-offline.Dockerfile` once the Rust image
is designed (deferred, see Scope).

### `.dockerignore`

Excludes `.git/`, `bin/`, `obj/`, and other non-source directories so the
`COPY . .` layer stays lean and isn't invalidated by build output that
shouldn't be in the image anyway (`AGENTS.md` already prohibits editing
generated `bin/`/`obj/` output).

### `docker/README.md`

Documents:
- The refresh vs. offline-build split and the exact commands from
  Architecture.
- When to refresh: after any `PackageReference` version change, addition, or
  removal — rerun `dotnet restore` per affected project (network), rebuild the
  image, commit the updated `packages.lock.json` file(s).
- That the Rust image is deferred (links to issue #11 and notes it'll follow
  the same refresh/offline-build split once designed).

## Error handling

- **Stale lock file:** `--locked-mode` restore (during refresh, which has
  network) exits non-zero if `packages.lock.json`'s content hash doesn't match
  the project's resolved references — surfaced as a `docker build` failure
  with NuGet's `NU1403` error; the fix is to refresh and commit, not to catch
  or suppress this.
- **Missing lock file:** verified empirically (four independent reproductions,
  including an isolated clean clone, on `mcr.microsoft.com/dotnet/sdk:10.0`
  SDK `10.0.302`) that `--locked-mode` does **not** catch a fully missing
  `packages.lock.json` — NuGet silently regenerates it and restore succeeds,
  which would let a deleted lock file quietly restore different package
  versions than intended. An explicit `RUN` step in the Dockerfile (right
  after `COPY`, before any restore) checks all six lock files exist and fails
  the build immediately with a clear message if one is absent, independent of
  NuGet's own behavior for this case.
- **Accidental network use in the offline step:** if any build/test/format
  invocation under `--network none` needed the network (e.g., an
  incompletely-restored package, or a future change that adds a package
  without refreshing first), it fails with a connection/DNS error from
  inside the container. That failure is the intended verification signal, not
  a bug to work around.

## Testing

No automated tests apply here — this is infrastructure, not application code.
Manual verification (documented as a checklist in `docker/README.md`,
following the same pattern as the tray icon issue's manual verification
steps):

1. `docker build -f docker/dotnet-offline.Dockerfile -t notification-agent-offline .`
   succeeds (network available).
2. Each `docker run --rm --network none ...` command from Architecture step 2
   succeeds: `.sln` build, `.sln` test, `.sln` format-verify, Windows project
   build, Windows test project build.
3. As a negative control, confirm that deliberately deleting a project's
   `packages.lock.json` and rerunning the image build fails at the
   file-existence guard step (proves a deleted lock file is actually caught,
   not silently regenerated).

## Non-goals / explicitly deferred

- The Rust toolchain and its offline image (pinned `rust-toolchain.toml`
  version, vendored crates, `x86_64-pc-windows-gnu` cross-compile target) —
  deferred until PR #4 (`rust-agent`) merges into `main`; tracked as follow-up
  work under issue #11.
- The "one combined image vs. two" question issue #11 raised — moot for now
  since only the .NET image is in scope; revisit once the Rust image is
  designed.
- Publishing the image to GHCR or any registry.
- A GitHub Actions (or other CI) workflow that builds/uses this image
  automatically — this repo has no CI pipeline today; out of scope here.
- Running `NotificationAgent.Windows.Tests` inside the container — already
  requires a real Windows machine per `AGENTS.md`, unrelated to network access.
- Supporting the image as a persistent, bind-mounted dev environment; it's
  meant to be rebuilt fresh each verification, like a CI image.
