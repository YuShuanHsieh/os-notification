Windows Desktop Notification Agent

Core NATS best-effort architecture for online-only Windows 11 toast notifications with acknowledgement-based latency tracing.

Format: arc42-inspiredTransport: Core NATSDelivery: at-most-onceTarget: Windows 11

1. Introduction and goals

A non-elevated per-user Windows agent starts after user sign-in, authenticates, subscribes to a user-scoped Core NATS subject, aggregates incoming events, and displays actionable Windows toast notifications.

Primary goal

Deliver low-latency notifications to users who are currently online.

Observability goal

Measure latency only for events acknowledged by an agent.

Non-goal

No offline queue, no guaranteed delivery, and no user presence service.

2. Architecture constraints

  • The agent runs in the signed-in user's interactive session and is non-elevated.
  • Core NATS provides at-most-once, best-effort delivery.
  • Messages published while no matching subscriber exists are intentionally discarded.
  • The backend must never claim that a successful publish means the toast was delivered.
  • The agent must use bounded queues and fixed concurrency.
  • The Windows account name is not a durable application identity.
Delivery contract: online-only, at-most-once, best-effort. Offline loss is an accepted product decision.

3. System context

4. Solution strategy

  1. Start one agent per signed-in Windows session.
  2. Authenticate with WAM/MSAL and resolve an immutable application user ID.
  3. Subscribe to notify.user.{userId}.desktop.
  4. Use Core NATS normal subscription for live fan-out to all active sessions.
  5. Aggregate and prioritize locally before calling the Windows API.
  6. Publish a lightweight acknowledgement after receive and toast submission.

6. Runtime views

6.1 Online delivery

Trusted app
  → Notification service
  → Core NATS publish
  → Active agent receives event
  → Event intake deserializes and deduplicates
  → Aggregator prioritizes / batches / replaces
  → Renderer calls AppNotificationManager.Show()
  → Agent publishes acknowledgement telemetry

6.2 Offline behavior

No active subscriber
  → Core NATS accepts publication
  → No agent receives the event
  → Event is permanently discarded
  → No acknowledgement arrives
  → Backend marks trace record as unobserved after timeout

6.3 Burst handling

Receive event
  → bounded queue
  → duplicate?
      yes → discard locally
  → send to Aggregator
  → critical → render immediately
  → important → higher-priority batch
  → normal → standard batch
  → progress/state → replace latest value
  → render only when needed

8. Authentication and authorization

Windows sign-in
  → WAM/MSAL silent token
  → Backend validates signature, issuer, audience, expiry, tenant, scope
  → Backend resolves applicationUserId and deviceId
  → Backend issues restricted NATS credential
  → Agent subscribes only to its assigned subject

The Windows username may be diagnostic metadata but is never trusted as proof of identity.

  "toastSubmittedAt": "2026-07-15T08:30:00.205Z",
  "status": "submitted_to_windows"
}

Latency calculations

Messaging latency
= agentReceivedAt - serverPublishedAt

Agent processing latency
= toastSubmittedAt - agentReceivedAt

Observed end-to-end latency
= toastSubmittedAt - producerCreatedAt

Latency percentiles include only acknowledged events. Unobserved publications affect the observation rate, not the latency distribution.

agent observation rate
= acknowledged / published

11. Delivery roadmap

Phase 1 — POC

  • Per-user agent and local toast.
  • WAM/MSAL authentication.
  • Core NATS subscription.
  • One producer request and one action button.
  • In-memory deduplication and basic aggregation.
  • Local structured logs.

Phase 2 — Reliability and observability

  • Bounded channel and fixed worker pool.
  • Persistent deduplication and aggregation state.
  • Telemetry acknowledgements and latency dashboards.
  • Credential refresh and revocation.
  • Resource guardrails and clean restart behavior.

Phase 3 — Enhancements

  • Server-side producer validation and rate limiting.
  • User category preferences.
  • Localization and richer notification templates.
  • Advanced multi-device/session routing.
  • Fleet health, feature flags, and synthetic probes.
